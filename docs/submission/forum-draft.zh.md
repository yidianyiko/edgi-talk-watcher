# 〖2026嵌入式大赛〗看守：用一句话设定视觉任务的 Edgi Talk 桌面伙伴

作者：Oliver  
硬件：英飞凌 Edgi Talk（PSoC Edge E84）  
系统：RT-Thread  
源码：https://github.com/yidianyiko/edgi-talk-watcher  
源码发布包：https://github.com/yidianyiko/edgi-talk-watcher/releases/tag/competition-2026-10-22

## 为什么做“看守”

生活中有一些很小的需求：桌上的东西被拿走时提醒我，有人进入画面时告诉我，原本放在那里的物品消失时留一张记录。

为这些临时需求一直盯着摄像头很麻烦，为每个目标训练一个模型也太重。我想做的，是把它们变成一句话就能设置的任务。

因此，这次作品聚焦一个功能：**用一句中文指定一个可见目标的出现或消失；检测到变化后提醒，并保存前后画面。**

我把它叫作“看守”。它放在桌面上，有一双会眨眼的眼睛，也有明确的工作状态。用户关心的是“替我看一下这件事”，而不必反复操作视频监控软件。

## 用户怎样使用

1. 在电脑上启动配套服务，板卡进入暂停状态。
2. 使用板卡屏幕的 SPEAK 入口录制一段语音，例如：“当画面中原本可见的手消失时提醒我。”也可以在网页输入任务。
3. 系统识别并校验任务，开始通过接在板卡上的 USB 摄像头间隔采样。屏幕显示状态，网页显示完整中文任务。
4. 产生新事件后，系统保存前后画面，将提醒送入板卡播放队列，并更新屏幕与网页历史。
5. 用户可以说“暂停看守”“继续看守”，也可以查看或删除历史事件。

目前语音录制窗口为 6 秒，任务限定为单目标出现或消失。预测、持续时长和多条件任务会被拒绝，避免系统接受超出当前能力的指令。

## Edgi Talk 承担什么

板卡负责 USB 摄像头采集、麦克风录音、Wi-Fi 通信、屏幕显示和提醒播放。电脑负责本地语音识别、任务编译与校验、视觉模型调用和事件存储。

```text
板卡麦克风 → Wi-Fi 中转 → 本地语音识别 → 任务 / 暂停 / 继续
板卡 USB 摄像头 → Wi-Fi 网关 → 视觉判断 → 事件与前后图片
新事件 → 提醒队列 → UART 控制与确认 → 板卡提醒播放
                  └→ 屏幕状态与网页历史
```

语音识别使用现有 Whisper 模型，视觉判断使用 Jev `jev-1.14.0`。不需要针对每个看守目标重新训练模型；中文任务编译一次后缓存复用。

屏幕上的两只眼睛会眨眼、左右看，并随状态变化。状态文字、事件计数和操作入口仍然保留，让用户知道设备正在看守、暂停还是遇到了问题。当前板端文字以 ASCII 为主，完整中文在网页显示。

这是一套板卡与电脑协作的原型。电脑服务需要保持运行，视觉判断需要访问外部模型服务。

## 让看守过程可控、可检查

实现中，我把“发生了什么”和“系统是否正常工作”分开处理：

- 遇到无法确定的画面，保留 uncertain 状态，不把它直接解释为没有事件。
- 新事件保存前后图片并去重；网页最多保留最近 100 条事件。
- 模型或网络异常会暂停，恢复后需要显式重新开始。
- 暂停时使旧会话失效，防止迟到的模型结果继续触发提醒。
- 重启默认暂停，避免用户不知道设备正在采集。
- 板端每次看守会话上限为 300 秒、60 次图像上传，包含 1 张参考帧和至多 59 次模型比较。

模型密钥留在电脑端，板端通过带鉴权的局域网入口上传图像和音频。当前使用面向可信局域网的 HTTP 中转。

## 实际做了哪些验证

**语音通路。** 已通过扬声器播放保存指令，让真实板卡麦克风录音，再经 Wi-Fi 上传到本地语音识别，执行任务、暂停和继续。录音已保存，后续调试可以复用，不需要反复找真人配合。不同口音和远场条件下的识别率尚未建立。

**视觉判断。** 三段保存录像共 678 张 JPEG，按原始时间约每 10 秒采样，进行了 67 次真实 Jev 判断。手消失、人员出现各保存 1 个事件，遮挡素材没有提醒。空场景和遮挡仍多次返回 uncertain，因此这些结果不能概括为“所有画面都判断正确”，也不是独立泛化准确率测试。

**板端摄像头与恢复。** 当前 V10 固件完成实际刷写校验。集成测试通过了七次开始与正常停止，并验证模型故障和中转进程退出后的显式恢复。该恢复测试包含一次真实 Jev 比较，返回 uncertain；其他受控视觉判断用于检查流程，不用于证明识别准确率。

**有界持续运行。** 300 秒预算测试保存 53 张原始帧，哈希全部匹配；51 次受控判断产生 1 个事件和 1 次 PLAY/DONE。实际帧时间跨度约 285 秒，不能写成连续 300 秒满帧率录像。默认启动器另完成三轮已存语音的开始与暂停流程。

**提醒和屏幕。** 提醒队列、去重、UART 播放控制以及录音与播放互斥已有验证；屏幕内容通过实板 framebuffer 读回。PLAY/DONE 代表播放控制链路完成，尚不等于独立确认扬声器音量和清晰度；framebuffer 图片也不是实体屏幕外部实拍。

详细实现和证据边界见源码中的 `docs/board-camera-integration.md`、`docs/board-voice.md`、`docs/event-announcement.md` 和 `CONTEXT.md`。原始私人场景、录音和运行凭据不随公开源码发布。

## 调试中解决的两个问题

接入 USB 摄像头时，曾出现没有完成帧却提前出队、随后停止流触发 HardFault 的问题。与官方预览例程对照后，定位到帧队列接收信号量的初始值不符合空队列状态。将其改为 0，并补充原生边界检查后，重复采集通过。

重复启停还暴露了 USB 取消过程中的中断竞争。当前版本在同步关闭后处理残留通道中断、串行化相关取消流程，并避免与厂商后台恢复任务同时操作控制器。修复后完成了上述七轮启停和故障恢复验证。相关补丁、构建步骤与失败记录说明均保留在项目资料中。

## 如何复现

先按仓库中的 `docs/submission/quickstart.en.md` 安装电脑端依赖、准备本地语音识别与私有配置。板端构建步骤见 `docs/submission/source-build-notes.en.md`，BSP 来自官方镜像并固定到记录的提交版本。

当前语音启动器在作者的 Windows/WSL 环境验证，尚不是跨电脑的一键安装包。换电脑时需按 quickstart 修改 `tools/run_product.py` 中 Windows Python 的固定路径，并检查相机工具的回退路径。准备好依赖、板卡固件、摄像头和网络后，在已安装依赖的 Python 环境运行：

```sh
.venv/bin/python -m tools.run_product --voice
```

默认使用接在板卡上的 USB 摄像头；需要电脑摄像头回退时，显式加上 `--camera-source pc`。网页入口为 `http://localhost:8765/`。

公开源码包含应用、工具、板端源文件、BSP 补丁、测试和文档；不包含厂商 BSP、模型权重、私人配置和原始测试录像。依赖保存素材的测试需要另外提供素材，源码包不能视作完整离线测试环境。

## 演示材料与当前边界

已准备 60 秒无声演示 `demo.mp4`，用字幕说明真实板端采集、PC 录像事件和屏幕读回图的来源。视频由保存素材组成，其中板端相机画面来自历史 V8 检查点；它不代表当前版本的连续现场实拍，也没有添加假装来自板卡的提示音。当前版本的集成结果以上述报告为准。

作品目前适合有界、低频采样的单目标看守任务。采样间隔内的短暂事件可能漏掉，尚未建立 24 小时可靠性。后续实体拔插、独立听感和最终实体触摸检查已不纳入本次交付验收，未执行的检查不记为通过。

我希望它在比赛之后仍能留在桌上使用：遇到一个临时的小需求，说清楚想看住什么；发生变化时得到提醒，并能打开前后画面确认。这就是“看守”目前想解决的一个点。
